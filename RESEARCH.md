# RESEARCH.md — Low-Level Design Practice & Automated Evaluation

## Executive Summary

Low-Level Design (LLD) and Object-Oriented Design (OOD) are critical skill requirements for senior software engineering roles. However, unlike Data Structures and Algorithms (DSA), where platforms like LeetCode and HackerRank provide instant automated feedback, LLD practice remains largely passive, unstructured, and subjective. Learners study static GitHub repositories or video walkthroughs without a mechanism to evaluate their own design submissions.

This research analyzes the current landscape of LLD education, identifies core structural gaps, evaluates deterministic vs. non-deterministic evaluation strategies, and establishes the rationale for **DesignCoach** — an automated, rubric-driven practice platform.

---

## 1. Existing LLD Practice Landscape

Current software engineering learners rely primarily on three mediums for LLD preparation:

| Medium | Example Platforms | Advantages | Limitations |
| :--- | :--- | :--- | :--- |
| **Static Code Repositories** | GitHub (`ashishps1/awesome-low-level-design`) | Standard reference code in Java/Python | Passive learning; assumes single "canonical" solution |
| **Video & Text Courses** | Educative.io, YouTube | Concept explanations, design patterns | No submission feedback loop or personalized evaluation |
| **Peer Mock Interviews** | Pramp, Interviewing.io | Live feedback, interactive discussion | High cost, non-deterministic peer quality, scheduling friction |
| **DSA Platforms** | LeetCode, HackerRank | Instant pass/fail evaluation, automated unit tests | Built for deterministic IO (Arrays/Trees); incapable of judging design trade-offs |

### Key Insight
> *"DSA platforms evaluate **output correctness**. LLD platforms must evaluate **architectural quality, trade-off reasoning, and structural decomposition**."*

---

## 2. Gaps in Current LLD Education

### Gap A: The Single Reference Solution Fallacy
Existing LLD repositories present a single reference implementation (e.g. "The Parking Lot Solution"). In reality, software architecture admits multiple valid implementations depending on constraints. A candidate might implement spot assignment using a **Strategy Pattern**, while another uses a **Priority Queue (Min-Heap)**. Both satisfy the requirement. Static solutions penalize valid alternative trade-offs.

### Gap B: Lack of Explainable Feedback
When learners practice independently, they face unanswered questions:
- *"Does my `ParkingLot` class take on too many responsibilities?"*
- *"Is my `Vehicle` hierarchy properly abstract, or am I over-engineering with unnecessary inheritance?"*
- *"Will adding a new vehicle type require modifying 5 different classes?"*

Without an experienced interviewer, learners repeat the same structural design smells across multiple problems.

## 3. Evaluation Methodologies: Deterministic vs. AI-Assisted

Evaluating open-ended design submissions requires balancing **rigor, determinism, and contextual reasoning**.

```
                   EVALUATION SPECTRUM
┌─────────────────────────────────────────────────────────┐
│ Deterministic Rules        Hybrid           LLM Reasoning│
├─────────────────────────────────────────────────────────┤
│ • Syntax validation   • Rubric scoring    • Smell identification│
│ • Mandatory sections  • Token weights     • Trade-off review    │
│ • Key presence        • Static analysis   • Evidence extraction │
└─────────────────────────────────────────────────────────┘
```

### Deterministic Evaluation (Rule-Engine)
- **Strengths**: 100% predictable, fast, zero token cost, reproducible.
- **Weaknesses**: Cannot understand semantic intent. Passing a length check does not prove that responsibilities are cohesive.
- **Role in Platform**: Used for pre-flight validation (checking section completeness, non-emptiness, minimum token thresholds).

### AI Evaluation (LLM-Driven against Structured Rubric)
- **Strengths**: Capable of semantic decomposition, identifying Single Responsibility Principle (SRP) violations, detecting tight coupling, and extracting quotes as evidence.
- **Weaknesses**: Stochastic output if unconstrained; potential hallucination.
- **Role in Platform**: Guided by an **8-dimension weighted rubric** and enforced via strict JSON response contracts to eliminate vagueness.

## 4. Why Evidence-Based Feedback is Essential

Standard generic AI responses (e.g., *"Score: 80/100. Good design!"*) fail to teach. To create an effective learning loop, feedback must be **evidence-based**.

Every feedback item generated by DesignCoach contains 4 components:
1. **Criterion Score**: Score breakdown against weight percentage (e.g. 14 / 20 for Responsibilities).
2. **Evidence**: Direct quotation or specific observations from the user's submission (e.g., *"`ParkingLot` lists payment processing and notification sending alongside spot allocation"*).
3. **Concern**: Clear explanation of the design smell (e.g., *"SRP Violation: Orchestrator class handles auxiliary billing"*).
4. **Actionable Suggestion**: Concrete refactoring guidance (e.g., *"Extract payment handling into a `PaymentService`"*).

## 5. Rationale for Submission Model Choice

We evaluated three potential submission formats for the MVP:

```
        Complex Diagram Editor          Freeform Code Textarea         Structured Text Submission
        (UML Canvas / Draw.io)         (Java/Python Files)             (Classes / Resp / Rel / Explanation)
       ────────────────────────       ───────────────────────          ────────────────────────────────────
Impact: Low efficiency for 2-day MVP  High parsing noise for evaluator Optimal abstraction for core LLD feedback
```

**Decision**: We chose **Structured Text Submission** for the MVP.
- **Why?** It isolates the core dimensions of LLD (Entity Identification, Responsibility Allocation, Relationship Mapping, and Trade-off Reasoning) without forcing the learner to debug syntax errors or spend 30 minutes dragging arrows in a canvas.
- **Extensibility**: The domain model is explicitly structured (`Submission` base entity) so `CodeSubmission` or `DiagramSubmission` can be added as child subclasses without refactoring the attempt lifecycle or evaluation engine.
